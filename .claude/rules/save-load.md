# Save/Load Rules (NON-NEGOTIABLE)

> Read the **Cards** section first. The prose below is reference detail.

Persistence is a cross-cutting foundation, not a feature of one module. Score, player rank,
difficulty strategy, settings, booster inventory, tutorial flags and level progress all read
and write through the same service. The rules below exist so that eight consumers can share
one mechanism without each inventing its own key naming, its own default, and its own
"what if there is no save yet" answer.

> **The generated `LocalSaveLoadDal` satisfies every card here as of 2026-09-02** — Card 7's temp-file swap
> and Card 8's `JsonException` fallback are both in `/setup-project` Step 4, each carrying the reasoning in
> a comment. Two caveats. A project generated **before** that date still ships the old body — the WRONG
> examples in Cards 7 and 8 are that body verbatim, so they double as a diff. And a **different** backend
> is not covered by this: Card 7 does not port to `PlayerPrefs` at all (no `File.Replace` equivalent), while
> Card 8 does, and a hand-written DAL has to carry it itself.

## Cards

### Card 1: Use the Framework Service — Never Touch PlayerPrefs or File Directly

**WHEN:** Any class needs to persist or read persisted data.

**WRONG:**
```csharp
// PlayerPrefs — untyped, no versioning, silently truncates, and platform-specific
PlayerPrefs.SetInt("score", _score);
var score = PlayerPrefs.GetInt("score", 0);

// Raw file access in a domain service — DIP violation, unswappable, untestable
File.WriteAllText(Application.persistentDataPath + "/score.json", JsonConvert.SerializeObject(data));
```

**RIGHT:**
```csharp
public sealed class ScoreService : IScoreService
{
    private readonly ISaveLoadService _saveLoad;

    public ScoreService(ISaveLoadService saveLoad) => _saveLoad = saveLoad;
}
```

The chain already exists in `_Framework/SaveLoadSystems/` and is not rewritten per project:

```
ISaveLoadService  →  SaveLoadService   (Tier 3, pure C#, logs via DLog)
ISaveLoadDal      →  LocalSaveLoadDal  (Tier 4, the only place File/JsonConvert appear)
```

Both are generated by `/setup-project` Step 4 — a project never writes them, and no consumer ever names the
concrete type.

**`PlayerPrefs` is banned in game code, not in a DAL — the ban is about the caller, not the API.**
`PlayerPrefsSaveLoadDal` is a legitimate `ISaveLoadDal` sibling of `LocalSaveLoadDal`, and the whole point
of the `*Dal` split is that such a sibling can exist. `check-save-load.sh` scopes its `PlayerPrefs` block to
`_GameFolders/Scripts/Games/` precisely so that `_Framework/SaveLoadSystems/` stays free to implement one.

When to reach for it, and when not:

| Situation | Backend |
|---|---|
| Default for everything | `LocalSaveLoadDal` — one JSON file per key, atomic write, real size limits |
| WebGL | `PlayerPrefsSaveLoadDal` — `persistentDataPath` writes go to IndexedDB and are **not flushed** until `Application.ExternalEval`/`FS.syncfs` runs, so a file write can silently vanish on tab close |
| A handful of small scalar settings on a platform where a file is overkill | `PlayerPrefsSaveLoadDal` |
| Anything large, or anything that must survive a crash mid-write | `LocalSaveLoadDal` — `PlayerPrefs` has no atomic-write story at all |

`PlayerPrefs` is not a lesser backend, it is a **different** one: per-key untyped string storage with a
platform-dependent size ceiling (a registry value on Windows, a plist on macOS/iOS), no directory, and no
`File.Replace` equivalent — so Card 7's atomicity cannot be implemented there, only approximated. Choose it
for what it is good at and say so in the module that registers it; do not let it become the default because
it looks simpler.

Whichever is registered, **no consumer changes** — that is the test that the boundary is in the right place.

**GOTCHA:** This is `architecture.md` Card 2.1 (Swappable Backend, `*Dal` suffix) applied to
persistence. The reason the split matters is not testability in the abstract — it is that
`CloudSaveLoadDal` must be addable later without touching a single service. If a service
references `File`, `Application.persistentDataPath`, or `JsonConvert`, that swap is already
impossible.

### Card 2: Every Persisted Type Is a `[Serializable]` class With an `int Version`

**WHEN:** Defining the shape of anything written to disk.

**WRONG:**
```csharp
// struct: `default` is indistinguishable from a real saved zero
public struct ScoreSaveData
{
    public int Score;
}

// class, but no Version: the first field type change is unrecoverable
[Serializable]
public sealed class ScoreSaveData
{
    public int Score;
}
```

**RIGHT:**
```csharp
[Serializable]
public sealed class ScoreSaveData
{
    public int Version = 1;   // bump on any breaking change: renamed/removed field, changed type
    public int Score;
}
```

**Why class and not struct, in order of weight:**

1. **`ISaveLoadDal.SaveData(string key, object value)` takes `object`.** A struct is therefore
   **boxed on every single save** — an allocation. A class is already a reference. The
   performance argument runs backwards from the intuition.
2. `default(T)` for a struct is a fully-populated valid-looking value. `Score = 0` reads
   identically to a real save of zero; a `strategy` field reads `0`, which is outside its
   own valid `1..7` range. A class returns `null`, and the "there is no save" signal survives.
3. Speed is not a criterion at all here: save/load runs at boot and at level end, never in
   `Update`. Neither the struct's layout nor the class's allocation is measurable.

**GOTCHA:** Adding a field never breaks parsing — Newtonsoft leaves an absent field at
`0`/`null` silently, which is exactly why `Version` is mandatory: without it you cannot tell
"this save predates the field" from "the value really is zero". Removing a field or changing
its type **does** throw. `Version` is the only thing that makes those recoverable.

### Card 3: `*SaveData` Is Persisted, `*Model` Is Not — Never Reuse the Name

**WHEN:** Naming a data class that holds score, progress, or any domain state.

**WRONG:**
```csharp
// One name, two lifetimes. Which one is on disk?
public sealed class ScoreModel { public int Score; public int Combo; }
```

**RIGHT:**
```csharp
[Serializable]
public sealed class ScoreSaveData { public int Version = 1; public int Score; }  // disk

public sealed class ScoreModel { public int Score; public int Combo; }           // session only
```

**GOTCHA:** Most domains need **both**, and they are not the same shape — the session model
carries a combo counter that must never be persisted, the save data carries a `Version` that is
meaningless at runtime. Naming both `*Model` guarantees that someone eventually persists the
combo counter or drops the version. This follows `csharp-unity.md` → Data Taxonomy, where
`*Model` is defined as "runtime writes it, dies with the session".

### Card 4: Keys Live in One static Helper — Never Inline

**WHEN:** Reading or writing any save key.

**WRONG:**
```csharp
_saveLoad.Save("score", data);          // magic string
if (_saveLoad.HasKey("Score")) { }      // and now a casing typo is a silent data loss
```

**RIGHT:**
```csharp
// Games/Concretes/Infrastructure/Helpers/SaveKeyHelper.cs
namespace Game.Concretes.Infrastructure.Helpers
{
    public static class SaveKeyHelper
    {
        public const string SCORE      = "score";
        public const string PROGRESS   = "progress";
        public const string SETTINGS   = "settings";
        public const string DIFFICULTY = "difficulty";
    }
}

_saveLoad.Save(SaveKeyHelper.SCORE, data);
```

**Placement is a hard rule, not a preference.** `Helpers/` may **not** be the first folder under
`Games/Abstracts|Concretes/` — the first segment must be a domain, never a layer or a catch-all
(`architecture.md` → Domain Folder Convention). Below a domain folder you are free, so the file
lives at:

```
Games/Concretes/Infrastructure/Helpers/SaveKeyHelper.cs   →  Game.Concretes.Infrastructure.Helpers
```

`Infrastructure/` is the correct domain: it already owns `AppModules`, `AppScope` and
`SceneModules`, and a cross-domain key contract belongs with the other cross-domain wiring.

**GOTCHA:** `check-domain-folder-structure.sh` does **not** block a top-level `Helpers/` —
`Common/`, `Shared/`, `Utils/`, `Helpers/`, `Misc/` are a documented, deliberate enforcement gap.
Hook silence is not approval. The rule file names `Helpers/` as an equally poor domain name;
the list is short only to keep false positives near zero.

### Card 5: One Key Per Domain — Never One Root Object

**WHEN:** Deciding how many things get written to disk.

**WRONG:**
```csharp
// Every module has to widen this class, and one Version field speaks for all of them
[Serializable]
public sealed class PlayerSaveData
{
    public int Version = 1;
    public int Score;
    public int Level;
    public int Strategy;
    public bool SoundOn;
    public bool TutorialSeen;
}
```

**RIGHT:**
```csharp
SaveKeyHelper.SCORE      → ScoreSaveData       (owned by the score module)
SaveKeyHelper.PROGRESS   → ProgressSaveData    (owned by the level flow module)
SaveKeyHelper.DIFFICULTY → DifficultySaveData  (owned by the difficulty module)
SaveKeyHelper.SETTINGS   → SettingsSaveData    (owned by the menu module)
```

Each module owns its own type, its own key, and its own `Version` — and migrates itself.

**GOTCHA:** The single-root shape looks tidier and costs more: every future module edits one
shared class (merge conflicts, and a `Version` bump that forces every other module's migration
to be reasoned about at once). The atomicity a single root buys is not needed here — settings do
not have to be consistent with progress. Pick the single root only when two fields genuinely
must be written or not written together.

### Card 6: Read Path Is `HasKey` → `Load`, Else the Config Default

**WHEN:** Loading persisted state at startup.

**WRONG:**
```csharp
// No existence check: a first-run player silently gets default(T) as if it were real data
var data = _saveLoad.Load<ScoreSaveData>(SaveKeyHelper.SCORE);
_score = data.Score;   // NullReferenceException on first launch

// Or: the default is hardcoded, so a designer cannot tune the starting value
_score = 0;
```

**RIGHT:**
```csharp
public void Initialize()
{
    if (_saveLoad.HasKey(SaveKeyHelper.SCORE))
    {
        var data = _saveLoad.Load<ScoreSaveData>(SaveKeyHelper.SCORE);

        // HasKey true + Load null is a REACHABLE state, not a paranoid guard: the file
        // exists, so HasKey answers yes, but Card 8's fallback returned default because the
        // content would not deserialize. Without this check the corrupt-save path is an NRE
        // instead of a clean restart — further from the cause than the exception it replaced.
        if (data != null)
        {
            _model.Score = data.Score;
            return;
        }
    }

    _model.Score = _config.StartingScore;   // ScoreConfiguration, via ConfigCatalog
}
```

Note the shape: the corrupt branch does **not** duplicate the default — it falls through to the
same line a first-run player reaches. One default, one place, whatever the reason for the miss.

**The default belongs to the domain, not to the service.** Only the score module knows that a
new player starts at `_config.StartingScore`; only the difficulty module knows that `strategy`
starts at `1`, not `0`. A service-level default would have to guess, and guessing produces a
value that is out of range for at least one consumer.

**GOTCHA:** First launch is not an edge case — it happens to 100% of players exactly once, and
it is the run where a missing existence check throws. Test it explicitly: a test that only ever
runs against an existing save file never executes this branch.

### Card 7: Writes Are Atomic — temp file, then Replace

**WHEN:** Implementing or reviewing the DAL's write path.

**WRONG:**
```csharp
// Truncates the file, THEN writes. Killed mid-write => a 0-byte file and the old save is gone.
public void SaveData(string key, object value)
{
    File.WriteAllText(GetFilePath(key), JsonConvert.SerializeObject(value));
}
```

**RIGHT:**
```csharp
public void SaveData(string key, object value)
{
    string path = GetFilePath(key);
    string temp = path + ".tmp";

    File.WriteAllText(temp, JsonConvert.SerializeObject(value));

    if (File.Exists(path)) File.Replace(temp, path, null);
    else                   File.Move(temp, path);
}
```

**GOTCHA:** Mobile operating systems kill a backgrounded process without warning, so "killed
mid-write" is routine, not exotic. This is also what makes `HasKey` → `Load` sound: a 0-byte
file makes `HasKey` return `true` while `Load` returns `null`, because `LoadData` treats empty
content as absent. Atomic write removes the only realistic cause of that mismatch, rather than
asking every call site to handle it.

### Card 8: A Corrupt Save Logs and Falls Back — It Never Throws Into the Game

**WHEN:** Deserialization fails.

**WRONG:**
```csharp
// Unhandled: JsonConvert throws, the scope never finishes building, the game does not open
public T LoadData<T>(string key)
{
    return JsonConvert.DeserializeObject<T>(File.ReadAllText(GetFilePath(key)));
}
```

**RIGHT:**
```csharp
public T LoadData<T>(string key)
{
    string path = GetFilePath(key);
    if (!File.Exists(path)) return default;

    string json = File.ReadAllText(path);
    if (string.IsNullOrEmpty(json)) return default;

    try
    {
        return JsonConvert.DeserializeObject<T>(json);
    }
    catch (JsonException ex)
    {
        DLog.Error(LogTag.SaveLoad, $"Corrupt save for key={key}, falling back to default. {ex.Message}");
        return default;
    }
}
```

The caller then sees `null` and takes its Card 6 default branch — the same path a first-run
player takes. **That only holds if the caller actually null-checks the `Load` result**, which is
why Card 6's read path does. `HasKey` answers "the file exists", not "the file parses", so the
two disagree exactly in this case; a caller that trusts `HasKey` alone turns a corrupt save into
a NullReferenceException. Found by comparing this rule against a project that had moved the
`catch` to the caller instead — its caller guarded both ways, ours guarded neither.

**GOTCHA:** Catch `JsonException`, not `Exception`. An `IOException` (locked file, permissions)
is a different problem with a different fix and must not be silently swallowed into a
default-value path. A bare `catch (Exception)` here is the empty-catch anti-pattern wearing a
log statement.

**Why a corrupt file exists at all**, in likelihood order — knowing the cause is what tells you
whether to handle it or prevent it:

| Cause | Handle or prevent |
|---|---|
| A field's type changed between builds (`int` → `long`) | **Prevent** with `Version` + migration (Card 2) |
| Half-written file (process killed, disk full) | **Prevent** with atomic write (Card 7) |
| Older build reading a newer save (version downgrade) | Handle — `Version` is higher than known |
| Hand-edited file (`persistentDataPath` is an open folder in Editor/desktop) | Handle |

### Card 9: Synchronous I/O Is the Deliberate Deviation — Record It

**WHEN:** Reviewing the DAL against `unity-async.md`.

`unity-async.md` requires UniTask for I/O. Save files here are a few hundred bytes, written at
boot and at level end — the frame cost the rule targets does not exist at this size. Staying
synchronous is therefore correct **and** a knowing deviation from a NON-NEGOTIABLE rule, which
means it goes in a decision record with its reasoning, never silently.

**GOTCHA:** Changing `ISaveLoadDal` to async later is a breaking change across every consumer.
If cloud saves, large blobs, or per-frame autosave ever enter scope, that is the moment to
revisit — and the decision record is what tells the next reader this was weighed rather than
overlooked.

## Consumers

Persistence is foundational precisely because it has no dependencies and many dependents. A
project that adds it "when the score module needs it" ends up with the save layer shaped by one
consumer's accident.

| Consumer | Persisted |
|---|---|
| Score | best score, cumulative score |
| Player rank / stars | per-level star rating shown on the level map |
| Difficulty strategy | the persistent strategy state machine value |
| Level selection | stateful cursor, dedup history |
| Menu / settings | sound, haptics |
| Boosters | inventory counts |
| Tutorial | seen flags |
| Level flow | current level number |

## Common Mistakes

| Mistake | Solution |
|---------|----------|
| `PlayerPrefs` or `File` called from a service | Inject `ISaveLoadService` (Card 1) |
| `struct` as the persisted type | `[Serializable]` class — `object` parameter boxes a struct anyway (Card 2) |
| No `int Version` on a save class | Add it at creation; bump on any breaking change (Card 2) |
| Naming the persisted class `*Model` | `*SaveData` persists, `*Model` is session-only (Card 3) |
| Inline key strings | `SaveKeyHelper` consts (Card 4) |
| `Helpers/` as a top-level folder under `Concretes/` | Put it under a domain: `Infrastructure/Helpers/` (Card 4) |
| One `PlayerSaveData` root every module widens | One key and one type per domain (Card 5) |
| `Load` without `HasKey` | `HasKey` → `Load`, else the config default (Card 6) |
| Hardcoded starting values | Defaults live in the domain's `*Configuration` asset (Card 6) |
| `File.WriteAllText` straight over the live save | temp file + `File.Replace` (Card 7) |
| Deserialization exception left unhandled | `catch (JsonException)` → log → default (Card 8) |
| `catch (Exception)` in the DAL | Catch `JsonException` only; an `IOException` is a different bug (Card 8) |
| Synchronous I/O left unexplained | Record the deviation from `unity-async.md` (Card 9) |
