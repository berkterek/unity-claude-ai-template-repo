# Grill Session 2 — v3 Plan (custom `graph-mcp-server.py`)

**Date:** 2026-06-18
**Subject:** v3 BREAKING rewrite — external `codebase-memory-mcp` removed; custom in-process MCP server backed by existing `graph.json` partition files.

> Note: Decisions 1–9 above belong to the superseded v1/v2 plan. The v3 architecture deleted the LSP/tree-sitter prerequisite, the GO/NO-GO gate, and `knowledge-graph-bridge.py`. The decisions below apply to the **current v3 plan**.

## Resolved Decisions (v3)

1. **Partition-file load failure semantics:** Fail fast on missing OR broken partition files. The server loads `graph.json` + `scenes.json` + `prefabs.json` at startup; if *any* of the three is missing, unreadable, or contains malformed JSON, the server fails fast at startup (non-zero exit / no successful stdio handshake). It must never serve a partial or empty graph. This makes the routing skill's MCP-availability check report State 2/3 (unavailable) and fall back to `graph-traversal.py` with the explicit stderr warning `"MCP bağlı değil — sonuçlar eksik olabilir"`. Extends Task 1 Step 2, which currently only names `graph.json` — broaden it to all three partition files plus JSON-parse errors.

2. **Staleness handling — reload-on-stale (overrides "load once + Claude Code restart"):** Each tool handler, before serving a query, checks `os.path.getmtime(graph.json)` against the mtime recorded at startup. If the file is newer, the server reloads all three partitions (`graph.json` + `scenes.json` + `prefabs.json`) and rebuilds the `forward`/`reverse`/`edges` adjacency state before answering. This replaces the plan's prior assumption that the in-RAM copy only refreshes on the next MCP server restart — handlers self-refresh on stale, so a `/build-knowledge-graph` run is reflected on the very next query without a restart.
   - **Trigger key:** mtime of `graph.json` only. `graph-builder.py` writes all three partition files together in the same run, so `graph.json` being newer is a sufficient proxy for the whole set being regenerated. (No need to stat all three on the hot path.)
   - **Reload reuses startup load path:** the same partition-resolution + adjacency-build code from Task 1 Step 2/Step 4 is factored into a `load_graph()` function callable both at startup and on stale-detect. Record the new startup mtime after each successful reload.
   - **Reload failure = keep last-good + warn:** if a mid-session reload hits a missing/broken partition (the Decision 1 fail-fast condition, but now at runtime rather than startup), the handler must NOT crash the server or serve a partial graph — it keeps the last successfully loaded in-RAM graph, answers from it, and emits a stderr warning that the reload was skipped due to a broken partition. (Startup still fails fast per Decision 1; only mid-session reloads degrade gracefully to last-good.)
   - **Plan impact:** Task 1 Step 2/Step 4 — wrap load logic in a reusable `load_graph()` and record startup mtime. Each of the four tool handlers (Step 4 BFS handlers) gains a leading stale-check. Strike the "in-RAM copy refreshes on the next server restart" sentence from the Decision Notes and the `## Staleness` paragraph at plan tail (line ~256); the `no --watch` decision stays (Claude Code restart is still the cold-start path; reload-on-stale is the warm-path refresh).

3. **Reload concurrency model — atomic rebind, lock-free (no `asyncio.Lock`):** When a stale-check fires, `load_graph()` rebuilds `g`, `forward`, `reverse`, `edges` into **fresh local objects** (new dict/set instances), then rebinds the four module-level names to those new objects in a single uninterrupted burst at the end. Handlers read the module-level names directly with no lock. This is safe because the `mcp` stdio server serializes tool calls on one asyncio event loop and the rebind block contains no `await` — it cannot be preempted mid-swap, so a handler always sees either the complete old graph or the complete new graph, never a half-rebuilt mix. The recorded startup mtime is updated in the same no-`await` burst, after the four name rebinds, so the next stale-check compares against the freshly loaded generation.
   - **Why lock-free:** an `asyncio.Lock` would add no safety here (single-threaded event loop, no preemption without `await`) and would only introduce a stall point + failure mode. Mutation in place (e.g. `forward.clear(); forward.update(...)`) is rejected — that *is* observable mid-rebuild. The whole point is to build aside and rebind, never mutate the live objects.
   - **Constraint this imposes on Task 1:** the JSON file reads and parsing inside `load_graph()` may use blocking `open()`/`json.load()` (acceptable — small files, cold path), but the function must complete the read+build into locals *before* the rebind, and the rebind + mtime-update sequence must be a plain synchronous block with no `await` anywhere between the first name rebind and the mtime write.
   - **Plan impact:** Task 1 Step 2/Step 4 — `load_graph()` returns a tuple of the four fresh objects (or sets them via a synchronous rebind helper); document the "no `await` in the rebind block" invariant as an explicit code comment requirement in the acceptance criteria.

4. **BFS code-duplication — Option A: shared `graph_bfs_core.py` (overrides "re-implement BFS inline / graph-traversal.py byte-identical"):** Extract the BFS traversal algorithm and its helpers into a new shared module, `.claude/graph/graph_bfs_core.py`, that **both** `graph-traversal.py` and `graph-mcp-server.py` import. The server no longer re-implements `bfs`/`cmd_*` logic inline (rejecting the plan's "Port BFS logic inline" Step 4 and the "never import graph-traversal.py" constraint); instead both consumers call the same single source of truth, eliminating the divergence risk that inline duplication creates.
   - **What moves into `graph_bfs_core.py`:** the `bfs(adj, start, max_hops)` algorithm and the pure traversal/query helpers — `all_nodes`, `check_node`, `suggest_node`, `require_edges`, and the four query cores (`callers` / `impact` / `path` / `god-nodes` computation) operating on already-loaded `g`/`forward`/`reverse`/`edges`. The module is pure: it takes loaded graph state as arguments and returns result objects; it does NOT do file I/O, CLI parsing, or stdout printing.
   - **`graph-traversal.py` is now modified (constraint relaxed):** the prior "byte-identical / do NOT touch" rule is replaced by **"CLI surface and output stay identical."** `graph-traversal.py` keeps its exact subcommand names, arguments, `--json` flag, stdout format, exit codes, and not-found/empty semantics — but its body changes to `import graph_bfs_core` and delegate the traversal logic instead of defining it inline. The File Map row and the multiple "graph-traversal.py unchanged / byte-identical" assertions across Goals, Task 1, Task 4, Task 6, and Implementation Notes must be reworded from "byte-identical" to "CLI surface + output identical; internals refactored to import `graph_bfs_core`."
   - **`graph-mcp-server.py` imports the same module:** the server's four tool handlers call into `graph_bfs_core` with the in-RAM `g`/`forward`/`reverse`/`edges` from `load_graph()`. SCRIPT_DIR discipline still applies for locating partition files; `graph_bfs_core.py` sits in the same `.claude/graph/` dir and is imported by module name.
   - **Parity test stays as a tripwire (Option B retained alongside A):** even with a shared core, Task 6 still adds an explicit parity test that runs each of the four queries through both `graph-traversal.py <subcommand> --json` and the corresponding `mcp__graph_mcp__*` tool and asserts structural equality. With a shared core this should be tautologically true, but the test is kept as a regression tripwire to catch a future change that re-introduces divergence (e.g. someone adds a server-side filter or a CLI-side post-process). The shared module is the prevention; the parity test is the detection.
   - **Plan impact:**
     - Task 1: rewrite Step 4 ("Port BFS logic inline") to "import and call `graph_bfs_core`"; drop the "never import/subprocess `graph-traversal.py`" line (importing the *shared core* is now required — importing `graph-traversal.py` itself is still forbidden, since that file owns CLI/I/O, not reusable logic).
     - File Map: add a `Create` row for `.claude/graph/graph_bfs_core.py`; change the `graph-traversal.py` row from "Unchanged / byte-identical" to "Modify — internals delegate to `graph_bfs_core`; CLI surface + output unchanged."
     - Task 6: add the parity-test step (B) as an explicit acceptance criterion; reword the "graph-traversal.py byte-identical" criterion to "CLI surface + output identical to pre-change."
     - Implementation Notes + Goals + Task 4: replace every "byte-identical" / "do NOT touch graph-traversal.py" phrasing with the relaxed "CLI surface + output identical" wording.

5. **MCP availability — collapse to 2-state model + Bash-emitted warning (overrides Task 4 Step 4's "3-state MCP availability check"):** The prior 3-state check (State 1 connected / State 2 registered-not-connected / State 3 not-registered) is removed. It collapses to two states keyed on a single observable signal — whether the `mcp__graph_mcp__*` tool is present in the session:
   - **State A — tool present →** call the MCP tool (`mcp__graph_mcp__callers` / `impact` / `path` / `god_nodes`). No warning.
   - **State B — tool absent →** echo the warning `"MCP bağlı değil — sonuçlar eksik olabilir"` **to stderr via Bash** (not as model prose), then run `python3 .claude/graph/graph-traversal.py <subcommand>` as the fallback.
   - **Why collapse:** "registered-not-connected" and "not-registered" were never distinguishable from the routing skill's vantage point — both manifest identically as "the tool isn't callable." Splitting them added a phantom branch with no behavioral difference. The only thing the skill can actually observe is tool presence/absence, so the model is exactly two states.
   - **Why Bash-emitted, not model prose:** the warning must hit stderr deterministically as a side effect of the fallback path, independent of whether the model remembers to narrate it. Emitting it from the same Bash invocation that runs `graph-traversal.py` (e.g. a leading `echo "..." >&2;`) guarantees the user sees it on every fallback, matching the v3 Decision 1/2/3 stderr-warning contract.
   - **Plan impact:** Task 4 Step 4 — replace the 3-state list with the 2-state A/B model above. Task 4 acceptance criterion "Fallback path … emits the stderr warning" stays but must now specify the warning is Bash-emitted to stderr from the fallback invocation, not narrated by the model. Task 6 Step 3 (flag-on / MCP-unavailable) — assert the stderr warning appears from the Bash fallback path. No change to `graph-traversal.py` itself; the `echo >&2` lives in the routing skill's documented fallback command, not in the Python.

6. **Warning-string ownership — Option (a) canonical-in-skill:** The literal warning bytes `"MCP bağlı değil — sonuçlar eksik olabilir"` have exactly one owner: the `echo "..." >&2` command documented in the routing skill (`knowledge-graph-hybrid.md`) as the leading clause of the fallback invocation. There is one canonical copy of the string, and it lives in the skill's emitted Bash.
   - **Plan + acceptance criteria reference by location, never re-quote the literal:** every place the plan currently re-quotes `"MCP bağlı değil — sonuçlar eksik olabilir"` (Task 4 Step 4, Task 4 acceptance criterion, Task 6 Step 3, Task 6 acceptance criterion, Implementation Notes "No silent degradation") must be reworded to point at "the warning string emitted by the routing skill's fallback `echo >&2`" rather than restating the bytes inline. This prevents the literal from drifting across N copies — if the wording ever changes, it changes in one place (the skill) and every reference still resolves.
   - **Task 6 asserts the skill's emitted bytes:** the Task 6 fallback-path check is reworded to assert that stderr contains *exactly the bytes the skill's `echo >&2` emits* — i.e. the assertion target is "whatever the canonical skill command outputs," not a second hand-typed copy of the string in the test step. The test reads the skill's command as the source of truth and confirms that command's stderr reached the user.
   - **Why (a):** keeping the literal in the skill's Bash (rather than in a Python constant in `graph-traversal.py`, or duplicated across plan + skill + test) means the string is emitted deterministically on every fallback as a Bash side effect (consistent with Decision 5's "Bash-emitted, not model prose"), and the plan documents intent without becoming a second authority that can disagree with the skill.
   - **Plan impact:** reword the five re-quote sites listed above to reference-by-location. Task 4 Step 4 keeps the literal exactly once, inside the documented `echo >&2` command (that is the canonical copy). Task 6 Step 3 / acceptance criterion change from "prints the explicit stderr warning `\"…\"`" to "stderr carries the exact bytes emitted by the skill's fallback `echo >&2` (no independently-typed copy of the string in the test)."

7. **Parity-harness consolidation — fold the stderr-bytes assertion into Decision 4's parity test (Option c):** Decision 4 already mandates a Task 6 parity harness that runs each of the four queries through both `graph-traversal.py <subcommand> --json` and the matching `mcp__graph_mcp__*` tool, asserting structural equality. Decision 6 separately requires Task 6 to assert that the fallback path emits exactly the bytes the routing skill's `echo >&2` produces. Rather than maintain these as two independent Task 6 steps, the stderr-bytes assertion is **folded into the same parity harness**:
   - **Single harness, three checks per run:** the Task 6 parity harness (a) greps the canonical warning literal out of `knowledge-graph-hybrid.md` (the Decision 6 single-owner source), (b) forces MCP-absent (State B — e.g. server unregistered or `mcp` uninstalled so the tool isn't present), invokes the fallback path, and (c) captures stderr and asserts it matches the grepped literal **byte-for-byte**. The structural-parity check (MCP tool output vs `graph-traversal.py --json`) runs in the MCP-present arm of the same harness.
   - **Why fold, not separate:** the parity harness is already the one place in Task 6 that exercises both backends side by side; adding the stderr-bytes assertion there keeps the "is the fallback contract honored" checks in a single runnable artifact instead of scattering them. It also makes the Decision 6 "reference-by-location, never re-quote" rule mechanically enforced — the harness *reads* the literal from the skill at test time rather than embedding a hand-typed copy, so a drift in the skill's string is caught by the same test that would otherwise silently pass.
   - **Grep is the source of truth, not a hardcoded expectation:** the assertion target is the byte sequence extracted from the skill file at test time. If the skill's `echo >&2` literal ever changes, the harness picks up the new bytes automatically and still asserts stderr == skill-emitted; there is no second copy of the string anywhere in the test to fall out of sync.
   - **Plan impact:** Task 6 — merge what would have been a standalone "assert stderr warning" step into the Decision 4 parity step. The parity harness step now reads: "for each of the four call-graph queries, (1) MCP-present arm: assert `mcp__graph_mcp__*` output is structurally identical to `graph-traversal.py <subcommand> --json`; (2) MCP-absent arm: grep the warning literal from `knowledge-graph-hybrid.md`, run the fallback, assert captured stderr equals the grepped bytes byte-for-byte." Task 6 Step 3 and its acceptance criterion collapse into this consolidated parity criterion rather than standing alone.

8. **`mcp` import / pip detection — once-and-cache, State-B-only, with specific diagnostic (Option b):** When `hybrid_graph` is on and State B (the `mcp__graph_mcp__*` tool is absent) is hit, the routing skill runs `python3 -c "import mcp" 2>/dev/null` **exactly once per session, lazily on the first State B trigger**, and caches the result for the rest of the session. The check is never run in State A (tool present → MCP is demonstrably working, so probing the import is pointless), and never run eagerly at session start (most sessions are State A and never need it).
   - **Non-zero (import fails → `mcp` not installed) emits a specific diagnostic before the generic fallback warning:** the fallback path prints a distinct line identifying the root cause — the `mcp` Python package is missing, so the server could never have started — *in addition to* the canonical generic warning. The diagnostic distinguishes "server crashed / unregistered" (generic) from "the `mcp` dependency was never installed" (specific, actionable: `pip install mcp`). Suggested diagnostic line: `"graph-mcp-server gerektiren 'mcp' paketi kurulu değil — pip install mcp"` emitted to stderr ahead of the generic `"MCP bağlı değil — sonuçlar eksik olabilir"`.
   - **Zero (import succeeds → `mcp` installed but tool still absent):** no extra diagnostic; the generic warning alone is correct, because the cause is registration/startup, not a missing dependency. The fallback to `graph-traversal.py` runs identically in both sub-cases.
   - **Cache scope = session:** the once-per-session result is held for the session lifetime. A `pip install mcp` performed mid-session is not re-detected until the next session — acceptable, because installing a dependency realistically pairs with a Claude Code restart anyway, and re-probing on every State B fallback would add a subprocess spawn to the hot path for zero practical benefit.
   - **Why State-B-only + cached (Option b) over probe-always or probe-never:** probing on every fallback wastes a subprocess spawn per query; never probing loses the ability to tell the user *why* MCP is down. Lazy-once-cached pays the probe cost at most once, only when it can actually matter (already in a fallback), and turns an opaque "MCP unavailable" into an actionable "install this package."
   - **Plan impact:** Task 4 Step 4 (the State A/B model from Decision 5) — extend State B to: on first entry this session, run the cached `import mcp` probe; if it fails, prepend the specific `mcp`-missing diagnostic to the stderr output ahead of the canonical generic warning. The generic warning's single-owner rule (Decision 6) is unaffected — the specific diagnostic is a *second, distinct* string with its own owner in the skill, emitted only on the import-fail sub-path. Task 6 — the parity harness's State-B arm gains a sub-case: force `mcp` absent (uninstalled) and assert the specific diagnostic precedes the generic warning on stderr; with `mcp` present-but-unregistered, assert only the generic warning appears.

9. **Flag-gated silence — `hybrid_graph` off/absent passes through with no warning, no probe (refines Decision 5):** The `hybrid_graph` gate check (Task 4 Step 1 / plan line 171) is the *first* routing step and it governs the entire warning + probe machinery, not just tool dispatch. There are two distinct gate outcomes:
   - **`hybrid_graph` off or absent → silent pass-through.** The routing skill skips all routing and dispatches every subcommand (including the four call-graph queries) to today's backend (`graph-traversal.py` for call-graph, `jq`/graph.json for Unity-semantic). It emits **no** `"MCP bağlı değil — sonuçlar eksik olabilir"` warning and runs **no** `import mcp` probe (Decision 8). This is the byte-for-byte-unchanged default path — a user who never opted in must see zero new stderr noise and pay zero probe cost. The MCP tool's presence/absence is not even consulted in this branch.
   - **`hybrid_graph` on AND `mcp__graph_mcp__*` tool absent (State B) → warn + probe.** Only here does the Decision 5 stderr warning fire and the Decision 8 lazy-once `import mcp` probe run. The warning means "you turned hybrid on but the MCP backend isn't reachable, so you're silently getting the partial fallback" — which is only actionable, and only true, when the user actually opted in.
   - **`hybrid_graph` on AND tool present (State A) → route to MCP, no warning** (unchanged from Decision 5).
   - **Why this refines, not contradicts, Decision 5:** Decision 5 phrased State B as *unconditionally* emitting the warning, but State B is only ever evaluated *after* the flag gate passes. Decision 9 makes that ordering explicit: the flag gate short-circuits before State A/B is ever computed. The warning is therefore conditional on `hybrid_graph == on`, not on tool-absence alone. An off-flag session with no MCP tool is **not** State B — it is "routing disabled," which is silent.
   - **Plan impact:** Task 4 Step 1 already reads the flag and skips routing when off/absent (line 171) — add an explicit sentence that "skip all routing" includes skipping the State A/B evaluation, the stderr warning (Decision 5), and the `import mcp` probe (Decision 8); the off-path consults nothing about MCP. Task 6 Step 2 ("Flag OFF regression") gains an assertion: with `hybrid_graph: false`, stderr is **empty** for all four call-graph queries (no warning, no diagnostic) even when the `mcp` package is uninstalled and the server is unregistered — proving the off-path is truly silent and probe-free.

10. **Default-value ownership — single source of truth in `graph_bfs_core` signatures (overrides per-surface defaults):** The `hops=3` and `top=10` defaults live in exactly one place: the function signatures of the query cores in `graph_bfs_core.py` (Decision 4's shared module). Neither the CLI nor the MCP surface restates the default value.
    - **MCP inputSchema declares `hops`/`top` as optional integers with NO schema-level default.** The tool's `inputSchema` marks the field optional (omittable by the caller) but does not encode `3`/`10` in the schema. When the caller omits the argument, the dispatcher passes nothing through (or passes `None`), and `graph_bfs_core` applies its signature default. The schema never competes with the core as a second authority for the number.
    - **Argparse defaults are replaced by `None`.** `graph-traversal.py`'s `argparse` `--hops`/`--top` options change from `default=3`/`default=10` to `default=None`. When the user omits the flag, the CLI passes `None` into the core, and the core's signature default fills it. The literal `3`/`10` no longer appears in the argparse setup.
    - **Core handles `None`:** the `graph_bfs_core` query functions take `hops: int = 3` / `top: int = 10` and treat an explicit `None` argument as "use the default" (i.e. the signature default applies whether the parameter is omitted entirely or passed as `None`). This is the one place the number `3`/`10` is written.
    - **Both CLI and MCP dispatcher inherit from one definition:** because both `graph-traversal.py` and `graph-mcp-server.py` call the same `graph_bfs_core` functions, changing a default (e.g. `hops` 3→4) is a one-line edit in the core signature and both surfaces pick it up automatically. There is no second copy in the argparse setup or the MCP inputSchema to drift.
    - **Why single-source over per-surface defaults:** declaring `default=3` in argparse AND `3` in the MCP schema AND `3` in the core signature creates three authorities that can silently disagree after an edit. Collapsing to one (the core signature) makes the CLI and MCP behaviorally identical by construction and keeps Decision 4's "shared core is the single source of truth" invariant intact for defaults, not just for traversal logic.
    - **Plan impact:**
      - Task 1 Step 3 (`mcp__graph_mcp__impact` "input: `node`, `hops` (default 3)" and `mcp__graph_mcp__god_nodes` "input: `top` (default 10)") — reword to "`hops` optional, no schema-level default; core supplies `3`" and "`top` optional, no schema-level default; core supplies `10`."
      - Task 1 / Decision 4: the four query cores moved into `graph_bfs_core` own the `hops=3` / `top=10` signature defaults and treat `None` as "apply default."
      - `graph-traversal.py`: argparse `--hops`/`--top` change to `default=None` (CLI surface + output unchanged — omitting the flag still yields hops=3 / top=10 behavior, now via the core, not argparse). This is consistent with Decision 4's "internals refactored, CLI surface + output identical" rewording.
      - Task 6 parity harness: omitting `hops`/`top` on both the CLI (`graph-traversal.py impact NODE --json` with no `--hops`) and the MCP tool (call with `hops` absent) must produce structurally identical output — i.e. both resolve to the same core default. Add this as an explicit parity sub-case.

11. **Not-found / empty-result error shape — successful tool result, never a JSON-RPC protocol error (Option a):** Handler outcomes that are *valid query answers* — node-not-found (with difflib suggestion), "No direct callers found," "No path … in the call graph," and any other empty-set result — are returned by the MCP tool handlers as **successful tool results** whose payload matches the CLI's `--json` shape. They are NOT raised as JSON-RPC errors. JSON-RPC errors are reserved exclusively for genuine faults — a malformed/missing partition file at startup (Decision 1 fail-fast, which never reaches a handler), an internal exception in the traversal core, an unparseable argument, etc.
    - **Why this is the correct boundary:** in `graph-traversal.py` the not-found and empty cases all exit `0` (success) — `check_node` prints the suggestion to stderr then `sys.exit(0)`; `cmd_callers` prints "No direct callers found" then `sys.exit(0)`. "Node not found" is a legitimate, expected answer to a well-formed query, not a protocol fault. The MCP surface must preserve that semantics: a caller asking about a node that doesn't exist gets a normal result describing the empty/suggestion outcome, not a transport-level exception that an MCP client would surface as a tool failure. Treating "not found" as a JSON-RPC error would (a) diverge from the CLI's exit-0 contract, (b) make the Decision 7 parity harness's MCP arm see a protocol error where the CLI arm sees a clean `--json` document, and (c) force every MCP client to special-case an expected query outcome as an error.
    - **Payload parity for the negative case:** because Decision 4 routes both surfaces through `graph_bfs_core`, the empty/not-found result object the core returns is identical regardless of caller. The handler wraps that core result as a successful MCP tool result. The suggestion text (`"Did you mean: …?"`) and the empty-array / empty-path shapes are part of the structured result, mirroring what the CLI emits to `--json` / stderr. (Where the CLI puts the suggestion on stderr and the data on stdout, the MCP result carries the equivalent structured fields in one successful result object — the *information* is identical even though the CLI's stdout/stderr split collapses into one structured payload.)
    - **Genuine-fault path stays distinct:** the Decision 1 startup fail-fast (broken partition) is a server-startup failure, not a per-call error, and manifests as State B (tool absent → fallback). A mid-call internal exception (e.g. corrupted in-RAM state, a bug in the core) is the only thing that should surface as a JSON-RPC error from a handler — and that is correct, because it *is* a genuine fault, distinguishable by the client from an ordinary "no results" answer.
    - **Plan impact:**
      - Task 1 Step 3 / Step 6 (output-format contract) — add an explicit sentence: handler not-found/empty/suggestion outcomes are returned as successful tool results matching the CLI `--json` shape; JSON-RPC errors are reserved for genuine faults (parse failure, internal exception, startup partition failure). Cross-reference the CLI's `check_node`/`cmd_callers` exit-0 behaviour as the parity target.
      - **Decision 7 parity harness — add a negative-case sub-arm:** alongside the existing positive structural-parity check (valid node through both backends → identical `--json`/result), add a sub-arm that runs an **unknown node** (a node guaranteed absent from the graph) through both backends and asserts (1) the suggestion / empty-result structure is identical between `graph-traversal.py <subcommand> --json` and the `mcp__graph_mcp__*` tool, and (2) the **MCP call returns a successful tool result, not a JSON-RPC protocol error** — i.e. the harness explicitly asserts the negative case is delivered as a result, distinguishing it from a genuine fault. This makes the exit-0 / result-not-error contract a mechanically enforced regression tripwire, not just prose.
