# Plan-Time Validation and Plan Coverage of the Gates

Moved verbatim from `.claude/CLAUDE.md` on 2026-10-08; the rule it supports is stated there in short form.

- **Path rules are validated at PLAN time, not only at write time.** `.claude/hooks/lib-path-rules.sh` is the single source of truth; it is called by `check-domain-folder-structure.sh` (write time) and by `.claude/scripts/validate-plan-paths.sh` (plan time, run by `/create-plan` and `/plan-module` at their SAVE step — after the plan is written, since neither script can read a plan that is not yet on disk — and by `/orchestrate` at Step 0b, before SCOPE_GATE, where the plan is already on disk). A folder-structure mistake is authored in `tasks.md` long before any file is written — the plan-time run is the one that prevents it. Legit exceptions are declared in `.claude/path-allowlist.txt` **and** `rules/architecture.md` → "Adding a Top-Level Folder", never invented silently. **2026-08-29:** `lib-path-rules.sh`'s `unity_path_allowlist_file()` located `path-allowlist.txt` via a bare `git rev-parse --show-toplevel`, which depends on the caller's cwd — a subagent's tool-execution context is not guaranteed to run from the repo root, so an empty result silently fell back to `.`, and a real, reviewed allowlist entry stopped matching inside a subagent even though it was correctly declared. Fixed by preferring `$CLAUDE_PROJECT_DIR` first (see the `subagent-depth` root-cause finding above — same bug class, same fix shape).
- **The gateguard's fact demands are also validated at PLAN time.** Same shape, same reason: `.claude/hooks/lib-gateguard-facts.sh` is the single source of truth; it is called by `gateguard.sh` (write time) and by `.claude/scripts/validate-plan-facts.sh` (plan time, run BLOCKING — by `/create-plan` and `/plan-module` at their SAVE step, **after** the plan is written, and by `/orchestrate` at Step 0b, before SCOPE_GATE). **"Before the gate" is not an option for a command that authors its own plan:** run against a folder that does not exist yet, this script prints `not found` and exits **0** — a silent green, never a block. `/plan-module` demanded exactly that until it was corrected; the gate had no teeth at all. A task that cannot name its callers or its wiring is a planning defect, so it is caught while the plan is editable rather than mid-pipeline where it deadlocks a subagent. There is **no cache and no receipt file** — the plan document *is* the manifest and every check is recomputed live. `NO TASKS FOUND` is not a pass; the script says so in its own output. Task declaration format: `docs/modules/_templates/tasks.md`. **Pass it a module plan folder (`docs/modules/NN-name/`) or a single `tasks.md`, never a broad root** — its directory walk collects `tasks.md` only and skips `_templates/` (the template's `[Domain]` placeholders own no folder and no `.asmdef`, so scanning the form would block on paths nobody intends to write; naming that file explicitly still scans it). The sibling `validate-plan-paths.sh` walks **every** `*.md`, not just `tasks.md`, so the same argument reaches much further there — see README → Plan-Time Validation.
- **Plan coverage releases the deny-then-allow gates.** When `gate-cleared` is open and the target file is named by a task in the plan, `unity_plan_covers` (in `_lib.sh`) lets `gateguard.sh`, `guard-critical-files.sh` and `check-config-protection.sh` (`.asmdef` branch only) pass without the Director-only retry. This is what makes `/orchestrate` and the `strict` profile compatible — before it, `guard-pipeline-direct-work.sh` blocked the Director while the gates blocked the subagent, so with a gate open *nobody* could write a `.cs`. `settings.json`, `manifest.json` and `.inputactions` are never released by coverage. Design record: `docs/superpowers/specs/2026-08-16-plan-time-fact-gate-design.md`.
> **Under the `strict` profile, coverage is not game code's preferred door — it is the ONLY one, and that was measured, not assumed.** `gateguard.sh` is a strict-level hook, so all of this applies to `strict` and to `/orchestrate`; under the default `standard` profile gateguard does not run at all and a subagent (depth > 0) writes freely. Stating it without that qualifier is wrong in both directions, and the first version of this note did — caught by CI, not locally, because the author's shell had `UNITY_HOOK_PROFILE=strict` exported and every check silently inherited it. With a gate open **and the strict profile active**, `_GameFolders/Scripts/**.cs` blocks at *both* depths: at depth 0 `guard-pipeline-direct-work.sh` stops the Director before `gateguard.sh`'s deny-then-allow retry branch is ever reached, and at depth > 0 that branch is Director-only by design. So the retry branch is **unreachable code in that region**, and until 2026-09-07 `gateguard.sh` still told the reader *"retry the same edit — it will pass"* there. It does not pass. A session spent four attempts following that sentence, then reset the depth counter twice trying to explain the result — the message named a door that does not exist, so every remedy it suggested was aimed at the wrong thing. Both the body and the final `BLOCKED:` summary now name the two real doors (declare the path in a `tasks.md` task, or spawn the pipeline agent) for that path pattern only; outside it the retry instruction is true and is kept. Pinned by three `gateguard.bats` tests, one of them a regression guard on the non-game-code branch.
> **2026-09-07, the same cwd bug class as `_lib.sh` and `lib-path-rules.sh` — third instance, in `lib-gateguard-facts.sh`.** `UNITY_PLAN_ROOT` defaulted to a bare relative `docs`, so `find docs -name tasks.md` resolved against the **caller's** cwd. A subagent's tool-execution cwd is not guaranteed to be the repo root (already documented twice above); when it is not, the find matches nothing and every path reads as "no task declares this" — a verdict about the plan, delivered when the plan was never opened. Measured against a real downstream plan whose tasks were correctly declared: `COVERED` from the repo root, `NOT COVERED` from anywhere else, same input, same plan. That is what makes it worse than a plain deadlock — it is **non-deterministic by cwd**, so one file sails through and the next one blocks three times, which reads as a plan defect and sends the reader to edit a file that was already right. Fixed the same way as the other two: `$CLAUDE_PROJECT_DIR/docs` first, bare `docs` only as a last resort, an explicit `UNITY_PLAN_ROOT` still wins. **The reason it survived two prior fixes of its own bug class: all 29 existing `lib-gateguard-facts.bats` tests set `UNITY_PLAN_ROOT` explicitly, so the default branch had no coverage at all** — when auditing for this class, a green suite proves nothing about a default nobody exercises. Also added `unity_plan_root_status()`: an unresolvable root now prints `PLAN ROOT NOT FOUND: <path>` plus "this is NOT a statement that the plan omits this path", because the silent version of this failure is the part that cost the session, not the failure itself. A sweep of the remaining 28 hooks using `git rev-parse --show-toplevel` found no fourth instance — 27 use it for a log tag (`basename`) or inside a user-facing message string, and `auto-load-skills.sh` anchors it on the file being written (`git -C "$(dirname "$FILE_PATH")"`), which is cwd-independent by construction.
> **2026-09-09, same library, different failure: a fact demand fired for a rename that was not happening — and the tests were shaped to the bug.** `unity_validate_task_facts`'s `FormerlySerializedAs:` demand (a real rule — without it every configured value in every scene and prefab silently resets to default) was triggered by a raw `grep -qiE 'rename|…|→'` over the **whole** task body. `unity_find_task_line` captures every sub-bullet, and `docs/modules/_templates/tasks.md` mandates a `Wiring:` field shaped ``via `Install()` → `Register<X>()…` `` — so the arrow alternative matched the template's own required field, and **every edit task written from this project's own template against a file containing `[SerializeField]` demanded a declaration for a rename nobody was making**. That is the default shape, not an edge case; the narrower trigger that surfaced it was an acceptance criterion reading *"level_1.npy temporarily renamed"*, which describes moving a data file to exercise an error path. Fixed by reading the **title line only** and dropping `→`: a field rename is by definition what the task *does*, and the arrow is ordinary prose punctuation here. **Two things outlast the fix.** The rule fires only at `mode=edit`, and plan-time validation runs before any target exists — so every task is `new` there and the branch is unreachable; it fires for the first time during the fix pass, after the file is on disk, which made a newly created file **uneditable by its own creation** — the same shape as the `PreToolUse` effective-content bug above, one layer up. And the branch was not uncovered: four bats tests exercised it, every one titled with a genuine `rename _speed to _moveSpeed`. A test can cover a branch and still be blind to it, because the fixture was written from the same assumption as the code — the third instance of that pattern in this file, after `reg.4`'s `ProbeInstaller.cs` and the 29 tests that always set `UNITY_PLAN_ROOT`. Three tests now pin the false-positive side, plus a regression guard that a real title-line rename still blocks.
